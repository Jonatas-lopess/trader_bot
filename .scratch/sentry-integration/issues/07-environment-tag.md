# 07: Correct `environment` tag on captured events

**Split from:** 04 (dashboard-readability follow-up split into two independent tickets — see
04's Comments).

**Category:** enhancement

**What to build:** Sentry's `environment` tag on every captured event currently defaults to
`"production"` — confirmed on ticket 01's verification event — because the Sentry
initialization options never set it explicitly. This is misleading on the only deploy target
that exists today (the workers.dev test route; PLANNING.md §12 gates a real production
deploy behind an unmet prerequisite), and will get more misleading once a production deploy
exists alongside it.

**Blocked by:** 01 (done — the wrapper this ticket's dashboard evidence came from)

**Status:** done

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Sentry-captured events should carry an `environment` tag that reflects which
deploy they came from, instead of Sentry's `"production"` default.

**Current behavior:** the Sentry client initialization options passed to the error-capture
wrapper don't set `environment`. Every captured event — from the workers.dev test route, from
local dev with a DSN bound, from any future production deploy — is tagged `"production"` in
the Sentry dashboard.

**Desired behavior:** the `environment` tag on a captured event reflects where that Worker
instance is actually running. At minimum, the workers.dev test-phase deploy must not read as
`"production"` in the dashboard. The distinguishing value should be sourced the same way this
repo already sources other per-deploy configuration (env binding or `wrangler.jsonc`
per-environment var — follow whatever precedent the existing Sentry DSN binding or other
provider config already sets), not hardcoded into a shared config file that's identical
across deploys.

**Key interfaces:**
- Wherever `Sentry.withSentry`'s (or equivalent) initialization options are constructed: add
  an `environment` field, sourced per-request off an env binding the same way `dsn` already
  is (not module-load time, not hardcoded).
- Whatever value distinguishes "workers.dev test route" from "not yet deployed" (no DSN
  bound, so moot) from "a real production deploy" once one exists.

**Acceptance criteria:**
- [ ] A captured event from the current (workers.dev test route) deploy does not tag
      `environment: "production"` in the Sentry dashboard
- [ ] The value is read per-request off env/config, not hardcoded at module load
- [ ] `pnpm test` and `pnpm run typecheck` pass
- [ ] PLANNING.md's stack/config table gets a row if this introduces a new env var or
      `wrangler.jsonc` var (mirror however ticket 01 recorded `SENTRY_DSN`)

**Out of scope:**
- Source-map upload (ticket 06 — separate blocker, needs a human-provisioned credential)
- Defining what production's `environment` value will be before production itself exists;
  just make sure the test-phase deploy isn't lying about being production

## Comments

> *This was generated by AI during triage.*

`environment` now read per-request off a new `SENTRY_ENVIRONMENT` env var
(`src/shared/sentry-environment.ts`'s `resolveSentryEnvironment`), wired into
`sentry.server.config.ts`'s `Sentry.withSentry` options alongside `dsn`/`enabled`. Falls back
to `'unconfigured'` — not Sentry's own `'production'` default — whenever the var is unset, so
the acceptance criterion ("does not tag `environment: 'production'`") holds even before
anyone sets the var anywhere.

**Not a wrangler.jsonc `var`** — this repo's `wrangler.jsonc` has no per-environment blocks,
so a value baked in there would be identical across every deploy target, the same problem
`PAYMENT_PROVIDER` solved by injecting `--var PAYMENT_PROVIDER:<value>` at deploy time
instead of committing it (ticket 09). `ci.yml`'s deploy step now does the same for
`SENTRY_ENVIRONMENT`, sourced from the "dev" GitHub Environment's variables — optional,
since the code-side fallback already satisfies the acceptance criterion without it; setting
it (e.g. to `workers-dev-test`) only sharpens the dashboard label beyond "not production."

`resolveSentryEnvironment` factored out as a plain, unit-tested function
(`src/shared/sentry-environment.test.ts`) rather than inlined in `sentry.server.config.ts` —
that file can't be exercised directly under `@cloudflare/vitest-pool-workers` (ticket 01's
own finding: it imports `@astrojs/cloudflare/entrypoints/server`, a Vite virtual module only
resolvable inside Astro's build), so the seam that can be tested is the pure function, same
shape as `factory.ts`'s `selectProvider`.

**Code review caught a blank-string gap**: `?? 'unconfigured'` only catches `null`/`undefined`,
not the empty string `.dev.vars.example`'s own `SENTRY_ENVIRONMENT=` line documents as the
"leave unset" convention — same gap `SENTRY_DSN`'s `Boolean(...)` gate doesn't have. Fixed to
`||`, with a test covering the blank-string case.
