### Finding

**`src/modules/licensing/robot-binary.ts` — `streamRobotBinary`'s R2-object-missing branch
is completely invisible today.** `streamRobotBinary` returns `{ ok: false }` when
`env.ROBOT_BINARY.get('robo-trader.ex5')` comes back `null`; `download.ts`'s
`resolveDownload` turns that into `status: 500`; `src/pages/download/[token].ts` turns *that*
into a bare `500` response with the string "Arquivo indisponível no momento." — no
`console.error`, no Sentry call, anywhere in that chain. Paging-worthy, not
expected/noisy: `robot-binary.ts`'s own header comment states there is exactly one fixed
object that "should always be there" (CONTEXT.md — "Robô: one program, not a family of
them"); its absence means every customer with a validly-redeemed download token gets a
silent 500 with zero server-side trace, indistinguishable from any other unexplained failure
until a support ticket arrives. Distinct from the token-expired/unknown-token 404 branch in
the same file, which is deliberately byte-identical and unlogged by design (ticket 02's own
"ordinary/expected, not an error" filter — a customer clicking a stale link is routine).

### Checked and clean / explicitly excluded

- **`src/modules/identity/`** — `magic-link.ts`'s `issueMagicLink` Resend-failure site is
  already covered (ticket 02). Every other branch (`requestMagicLink`'s throttle/no-match,
  `redeemMagicLink`'s invalid/expired/already-used token) deliberately collapses distinct
  "ordinary" outcomes into the same generic response/redirect by design (spec.md User Story
  3) and is never logged today, by the same "expected traffic, not an error" reasoning as
  ticket 03's 429 exclusion. No new caught-failure site here.
- **`src/modules/licensing/`** — no activation or seat-limit code exists yet to audit:

  caught failures. `download-tokens.ts`'s expired/unknown-token branch mirrors
  `magic-link.ts`'s, same "deliberately indistinguishable, ordinary" reasoning. The one real
  finding in this module is `robot-binary.ts`, above.
